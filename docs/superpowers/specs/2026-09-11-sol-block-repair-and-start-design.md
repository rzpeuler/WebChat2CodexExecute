# Sol 阻塞自动修复与启动入口设计

## 1. 目标

为可由 Sol 重新生成文本解决的阻塞增加一次性自动修复，并让 Dashboard Graph 显示修复分支；同时让启动动作立即从“读取 Sol”节点执行一轮，而不是先返回等待状态。

本次不授予 Sol 或自动修复分支任何本地文件删除能力。治理一致性块中的修复动作只允许让 Sol 从 `files[]` 中移除不安全条目或修正合法条目的内容。

## 2. 自动修复边界

### 2.1 可自动修复

- Writing Block 外部多余文本、JSON 无效、字段缺失/类型错误、块数量冲突等协议错误；
- `GOVERNANCE_RECONCILIATION_PATH_OUTSIDE_PROJECT`；
- `GOVERNANCE_RECONCILIATION_PATH_PROTECTED`；
- `GOVERNANCE_RECONCILIATION_SHA_CONFLICT`。

软件向 Sol 发送包含错误码和诊断的修复提示。路径错误要求 Sol 移除不安全的 `files[]` 条目，不得删除本地文件；SHA 冲突要求 Sol 重新读取并填写当前文件 SHA。修复提示要求只输出一个合法的预期 Writing Block，不输出块外说明。

### 2.2 不自动修复

认证、网络、上下文过长、会话丢失、Git 分支/基线变化、文件不存在、二进制文件、权限问题、提交/推送失败、应用器不可用和外部账户/API Key 配置问题继续进入现有人工处理或常规重试路径。

每个原始输出只允许发送一次修复提示。修复后的新输出再次触发同类可修复错误时，不再向 Sol 发送第二次修复提示，直接进入 `NEEDS_USER_ACTION` 并说明需要人工处理。

## 3. 状态和 Graph

持久化一条最小自动修复记录：原始输出 key、错误码和尝试次数。修复成功后清除；应用重启后仍能识别同一原始输出已经尝试过。

Graph 增加 `repair-sol` 节点。正常轮次保持待处理；触发修复后高亮该节点，并展示错误码、修复次数、发送状态和等待新输出状态。收到新输出后回到读取/解析流程；修复后的输出再次失败则该节点显示需要用户处理。

修复提示发送成功后，循环保持运行并等待新的 Sol 输出。发送失败仍按现有异常路径暂停，不伪造修复成功。

## 4. 启动行为

普通“启动”会：

1. 设置循环为运行中；
2. 创建新的读取轮次并激活 `read-sol`；
3. 立即执行一次 Sol 状态读取；
4. 读取结果为思考中/无新输出时才进入 `wait-sol`。

待同步的治理或代码上下文继续优先恢复对应同步节点，不被普通启动覆盖。

## 5. 验收标准

1. 路径越界或保护路径错误最多向 Sol 自动发送一次修复提示，提示明确写“移除输出条目，不删除本地文件”。
2. 修复后的输出仍然经过完整 Writing Block、路径、基线和 Git 校验。
3. 第二次同类错误进入人工处理，且不会再次调用 `sendMessage`。
4. Graph 有可识别的 `repair-sol` 节点，并显示当前修复阶段。
5. 启动调用后立即发生一次 `edge.observe()`，不会只返回等待而等待下一次轮询。
6. 现有路径安全、治理应用、状态持久化、Dashboard 和完整测试继续通过。
