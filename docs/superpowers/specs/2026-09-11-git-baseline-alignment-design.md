# Git 提交同步与基线对齐设计

日期：2026-09-11  
状态：已确认，待实现

## 1. 背景

自动循环依赖 Git 基线来确认 Sol 任务书与本地项目状态一致。项目在人工处理阻塞、手动提交、推送或恢复文件后，软件内存中的基线可能落后于实际仓库，从而产生 `BASELINE_CHANGED`。

当前需要两个面向人工恢复的独立操作：

1. 将工作区全部变更提交并推送到当前远端分支；
2. 在工作区干净后，让软件读取并采用最新 Git 基线。

这两个操作不属于自动循环，不改变自动循环的节点、顺序或等待逻辑。

## 2. 目标与非目标

### 目标

- 提供“提交并同步 Git”按钮，提交工作区全部变更，包括代码、治理文档、备份文件和删除记录。
- 提供“对齐最新基线”按钮，在工作区干净时刷新软件内存中的本地 HEAD、远端跟踪状态和项目身份信息。
- 在 commit、push 和基线刷新过程中提供阶段性状态，防止重复点击。
- 让用户明确知道旧任务是否因 HEAD 变化而失效。
- 保持现有自动循环工作流不变。

### 非目标

- 不自动触发下一轮自动循环。
- 不自动让 Sol 重新生成任务书。
- 不自动 pull、merge、rebase 或 force push。
- 不自动修改当前项目文件内容。
- 不把这两个操作添加为 Loop Graph 节点。

## 3. 用户操作语义

### 3.1 提交并同步 Git

按钮名称：`提交并同步 Git`

适用场景：自动循环暂停、阻塞或空闲，且没有其他后台操作。

执行流程：

```text
读取工作区变更
  -> 显示变更摘要并要求一次确认
  -> git add -A
  -> git commit
  -> git push 当前分支的已配置远端
  -> 重新读取本地 HEAD、远端跟踪分支和工作区
  -> 刷新软件基线
```

提交范围是当前仓库全部变更：新增、修改、删除、重命名以及 `.web-chat2codex/backups` 下的备份文件。

工作区干净时不创建空提交，直接反馈“工作区已干净，无需提交”。

提交信息使用固定、可识别的自动信息：

```text
chore(web-chat2codex): sync project changes
```

如果本地 commit 成功但 push 失败，必须保留“本地已提交、远端未同步”的状态；再次操作只允许继续完成 push，不重复制造 commit。

### 3.2 对齐最新基线

按钮名称：`对齐最新基线`

执行前提：工作区必须干净，项目必须是有效 Git 仓库，并且当前分支、远端和目标配置可读取。

执行流程：

```text
检查工作区干净
  -> 读取当前分支、本地 HEAD、远端 URL 和远端跟踪提交
  -> 刷新软件内存中的 baseline
  -> 标记旧任务书需要重新生成（如 HEAD 已变化）
```

该动作只更新软件状态，不修改 Git，不发送 Sol 消息，不自动开始循环。

## 4. 与自动循环的边界

自动循环的现有节点和顺序保持不变：

```text
读取 Sol -> 解析任务书 -> 应用治理/架构更新 -> 执行 Luna -> 同步代码 -> 通知 Sol
```

两个 Git 按钮是循环外的人工恢复工具。它们完成后，用户仍需手动点击“启动”或“继续执行”。

如果 commit/push 或外部操作导致 HEAD 变化：

- 软件刷新当前基线；
- 当前旧任务书标记为失效；
- 不自动改写旧任务的 `base_commit`；
- 用户需要让 Sol 根据新的 HEAD 重新生成任务书。

## 5. UI 状态与并发控制

- 自动循环、Codex、治理同步或另一项 Git 操作运行时，两个按钮禁用。
- 操作进行中显示当前阶段和不可重复点击原因。
- “提交并同步 Git”阶段显示：检查工作区、提交本地变更、推送远端、刷新基线。
- “对齐最新基线”阶段显示：检查工作区、读取 Git 状态、刷新基线。
- 自动循环阻塞时，按钮作为阻塞处理工具显示在操作区，不改变当前 Loop Graph 节点。
- 成功后显示旧基线、新基线、分支、远端同步结果和下一步建议。

## 6. 异常策略

### 工作区与项目异常

- 工作区不干净：拒绝“对齐最新基线”，展示具体路径，并引导“提交并同步 Git”。
- Git 仓库无效：显示项目路径和接管提示。
- 远端缺失：停止并提示配置远端。
- 当前分支与目标分支不一致：停止，不自动切换分支。

### 提交与推送异常

- commit 失败：保留工作区，不刷新基线，显示 Git 输出摘要。
- push 失败：标记本地提交已完成、远端未同步，允许再次推送。
- 远端领先或发生冲突：停止，不自动 pull、merge、rebase 或 force push。
- 操作超时：保留阶段状态，防止重复提交；用户确认 Git 状态后再继续。

### 任务基线异常

如果当前任务书的 `base_commit` 不等于刷新后的 HEAD：

```text
当前基线：<new sha>
任务书基线：<task sha>
结果：旧任务书已失效
建议：让 Sol 根据当前基线重新生成任务书
```

## 7. 状态模型建议

新增操作状态应与自动循环状态分离，至少包含：

- `IDLE`
- `CHECKING_WORKTREE`
- `COMMITTING`
- `PUSHING`
- `ALIGNING_BASELINE`
- `COMPLETED`
- `FAILED`

状态应持久化足够的阶段信息，以便软件重启后能区分：未开始、已提交未推送、已推送待刷新和已完成。

## 8. 验证计划

实现后至少验证：

1. 干净工作区不产生空提交；
2. 同时包含新增、修改、删除和备份文件时，`git add -A` 全部纳入提交；
3. commit 失败不刷新基线；
4. push 失败后可只重试 push；
5. 远端冲突不会自动合并；
6. 对齐动作拒绝脏工作区；
7. HEAD 变化后旧任务被标记失效；
8. 操作期间重复点击被拒绝；
9. 软件重启后能恢复“本地已提交、远端未同步”等中间状态；
10. 自动循环节点和现有 Sol/Luna 流程回归测试不受影响。
