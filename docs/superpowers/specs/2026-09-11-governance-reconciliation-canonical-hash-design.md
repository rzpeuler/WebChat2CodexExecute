# 治理一致性覆盖的规范化哈希校验设计

## 目标

治理一致性检查用于处理 `docs/governance` 之外、被 Sol 判断为会影响治理或开发行为的文档。Sol 返回完整替换内容后，软件必须确认目标文件仍然是 Sol 检查时看到的版本，再执行覆盖。

本次改进只解决换行符、BOM 和文本编码差异导致的误报，不放宽对实际内容变化的保护，也不恢复自动修复分支。

## 当前问题

当前应用器对目标文件的原始字节直接计算 SHA-256。相同文本在以下情况下会产生不同哈希：

- CRLF 与 LF；
- UTF-8 BOM 与无 BOM；
- Git 或编辑器造成的换行转换。

因此，远端内容、本地工作区内容和 Sol 读取到的内容语义一致时，仍可能触发 `GOVERNANCE_RECONCILIATION_SHA_CONFLICT`。

## 方案

保留 `sha256_before` 字段，但将其定义为 `canonical-text-v1` 规范化文本的 SHA-256，而非原始文件字节的 SHA-256。

规范化规则：

1. 文件必须是非空、合法 UTF-8 普通文本；
2. 去除 UTF-8 BOM；
3. 将 CRLF 和孤立 CR 统一为 LF；
4. 保留正文内容、空格和末尾换行，不做 trim；
5. 对规范化后的 UTF-8 字节计算 SHA-256。

替换规则：

- 应用前仍执行一次目标文件重新读取和哈希校验；
- 规范化哈希相同但原始字节不同，允许替换；
- 实际文本内容不同，继续抛出 `GOVERNANCE_RECONCILIATION_SHA_CONFLICT`；
- 替换内容写入 UTF-8，并尽量沿用原文件是否带 BOM 及其换行风格，减少无意义 diff；
- 所有路径安全、保护路径、备份和事务回滚规则保持不变。

## 协议与提示词

- Writing Block 结构不增加新的必填字段，避免扩大 Sol 输出复杂度；
- 治理一致性模板和 Sol 提示词明确 `sha256_before` 使用 `canonical-text-v1`；
- 提示词要求 Sol 基于其实际检查到的完整文本计算规范化哈希，不允许猜测；
- 对无法可靠读取或计算哈希的文件，Sol 应返回 `BLOCKED`，而不是伪造 `CHANGES_REQUIRED`。

## 错误与诊断

SHA 冲突信息继续区分“目标文件内容已变化”和“目标文件不存在”等已有错误。软件内部可同时记录原始字节哈希、规范化哈希、BOM 和换行风格，用于诊断，但不把这些内部信息要求 Sol 输出。

如果规范化哈希不一致，仍必须暂停并由用户处理；不能以“语义看起来相同”为理由强制覆盖。

## 兼容与迁移

旧 Writing Block 使用原始字节哈希，无法可靠判断其哈希模式。升级后旧的待处理一致性块在哈希校验失败时应提示重新执行治理一致性检查，而不是自动转换或自动覆盖。

## 测试范围

- LF、CRLF、孤立 CR 的等价性；
- UTF-8 BOM 与无 BOM 的等价性；
- 空格、正文字符和末尾换行变化仍会冲突；
- Git 自动换行场景下的替换；
- 应用前文件被并发修改时仍然冲突；
- 多文件替换、备份、失败回滚和路径安全回归；
- Sol 模板对 `canonical-text-v1` 的说明和现有 JSON 校验回归。

## 非目标

- 不修改 `docs/governance` 的权威路径规则；
- 不改变 Sol 候选文件筛选职责；
- 不自动删除不安全文件；
- 不恢复或扩展自动修复分支；
- 不把远端 Git 同步状态当作本地覆盖安全校验的替代品。
