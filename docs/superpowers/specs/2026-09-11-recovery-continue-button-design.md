# 恢复执行按钮链路设计

## 背景

旧版治理一致性入口状态迁移后，Dashboard 可以显示解析任务书节点的“继续执行”按钮，但点击可能停留在前端确认或动作快照预检，未进入编排器的恢复方法。需要修复这条交互链路，使用户能够继续已识别的中断执行。

## 目标与边界

- “继续执行”点击后直接提交 `continue-interrupted` 命令，不再依赖浏览器二次确认弹窗。
- 后端继续验证恢复记录、暂停状态和恢复节点；前端绕过确认不改变实际执行权限。
- 点击后立即显示处理中并锁定同一命令，完成或失败后刷新 Dashboard。
- 不改变普通启动、暂停、重试和治理一致性检查的确认策略。

## 交互与数据流

1. 用户点击解析任务书节点旁的“继续执行”。
2. Renderer 检查快照动作状态；若可用，加入 pending 集合并调用 IPC。
3. Main process 校验命令并调用 `continueInterrupted()`。
4. 编排器确认存在等待恢复的记录后恢复中断节点并继续处理最新 Sol 输出。
5. Renderer 显示结果并拉取最新快照；处理中期间按钮不可重复点击。

若恢复条件不满足，后端返回稳定的中文不可用原因，Renderer 显示该原因而不改变状态。任意异常都必须结束 pending 状态并刷新快照，避免按钮永久锁定。

## 验证

- 覆盖 `continue-interrupted` 不需要前端确认即可构造并发送。
- 覆盖处理中期间同一命令不能重复提交。
- 保留并通过现有 Dashboard 命令校验、编排器恢复和状态迁移测试。
