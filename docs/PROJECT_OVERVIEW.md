# web_chat2codex_exe 项目介绍

## 1. 项目背景

`web_chat2codex_exe` 是一个运行在 Windows 上的 Electron 桌面自动化编排器，用于连接 ChatGPT Web 对话和 Codex CLI，减少开发过程中在产品规划、代码执行、结果传递和 Git 同步之间的人工搬运工作。

项目采用“双角色 + 编排器”的协作模式：

- **Sol（Web Chat）**：负责产品方向、顶层架构、治理规则、任务拆分、验收判断和下一轮规划。
- **Luna（Codex CLI）**：负责按照任务书修改代码、执行测试、生成任务报告，并返回机器可解析的执行结果。
- **ORCHESTRATOR（本软件）**：负责读取 Sol 输出、校验协议、启动 Luna、管理 Git 基线、提交并推送代码、通知 Sol，以及持久化循环状态。

理想的开发流程是：用户与 Sol 确认总体方向后，软件自动执行下面的循环：

```text
Sol 生成任务书
    ↓
ORCHESTRATOR 解析并校验任务书
    ↓
Codex/Luna 执行任务并生成报告
    ↓
ORCHESTRATOR 提交、推送代码和报告
    ↓
通知 Sol 开始验收并规划下一轮
```

## 2. 核心功能

### 2.1 项目初始化与接管

软件支持新项目初始化和已有项目接管：

- 选择本地项目目录，而不是手工输入目录字符串。
- 配置并校验远端 Git 仓库地址、分支和本地仓库状态。
- 新项目可以先 Clone 远端仓库，再安装标准治理文档。
- 已有项目严格使用 `docs/governance` 作为权威治理目录。
- 接管已有项目时，可备份原有治理目录，再安装标准治理结构。
- 项目配置保存在本机 `projects.json` 中；同一本地目录的配置采用覆盖更新，启动时默认恢复上次项目。

### 2.2 Sol 提示词与治理模板

软件生成给 Sol 使用的系统提示词，提示词包含：

- Sol、Luna 和 ORCHESTRATOR 的职责边界。
- 治理目录和 Writing Block 模板路径。
- 单轮最多生成一个 `LUNA_TASK` 的约束。
- 架构冻结、治理变更和治理一致性检查的处理规则。
- Luna 默认放行普通工程决策，但外部账号、API Key、高风险操作和真正的范围冲突必须阻塞。
- Luna 不得自行执行 `commit`、`push`、`amend`、`rebase` 或强制推送。

Writing Block 的模板实际保存在项目治理目录中。软件负责校验模板和 JSON 结构，Sol 只需要根据模板填写内容，不依赖提示词记忆完整字段表。

### 2.3 Edge Web Chat 会话绑定

软件通过专用 Edge profile 连接用户已经登录的 ChatGPT Web 会话：

- 用户可以在弹出的 Edge 中完成正常登录。
- 软件识别当前打开的 ChatGPT Project 会话，并绑定目标会话。
- 不保存用户密码；登录状态由 Edge profile 的 Cookie 维持。
- 软件持续读取 Sol 最新消息和页面状态。
- 支持识别完成、思考中、网络异常、上下文过长、登录失效和会话缺失等状态。

如果对话上下文过长，软件可以按照上下文恢复策略创建或切换到新的会话，并继续传递必要输入。

### 2.4 Writing Block 协议解析

所有面向 ORCHESTRATOR 的机器指令都必须使用如下边界：

```text
[WRITING_BLOCK type="LUNA_TASK"]
{完整 JSON 对象}
[/WRITING_BLOCK]
```

当前支持的主要类型包括：

- `LUNA_TASK`：交给 Codex/Luna 执行的单个任务。
- `GOVERNANCE_CHANGE`：治理文档变更。
- `GOVERNANCE_RECONCILIATION`：检查治理目录以外的文档是否与当前治理规则冲突。
- `ARCHITECTURE_FREEZE`：架构冻结或架构文档更新。
- `BLOCKED`：Sol 明确报告无法安全继续的原因。

块正文使用严格 JSON，而不是 YAML。软件会检查：

- 开始和结束标记是否成对。
- 是否存在重复或嵌套 Writing Block。
- 块正文是否为合法 JSON。
- 任务字段、任务类型、路径、基线和报告路径是否有效。
- 是否出现不应存在的块外内容或非法文本。

### 2.5 自动循环 Loop Graph

前端使用 Loop Graph 展示当前自动化进度。主要节点为：

1. `read-sol`：读取并识别 Sol 最新输出。
2. `parse-task`：解析 Writing Block、任务类型和执行历史。
3. `apply-updates`：应用治理或架构更新。
4. `sync-governance`：提交并推送治理文档。
5. `run-luna`：启动 Codex CLI 执行任务。
6. `sync-code`：校验、提交并推送代码和任务报告。
7. `notify-sol`：把最新提交、报告和测试信息发送回 Sol。
8. `wait-sol`：等待 Sol 生成下一轮规划。

当前节点会高亮显示，节点周围会显示任务编号、报告路径、提交哈希、测试状态、错误原因、计时器和恢复信息。

自动修复分支不作为独立可见节点；可自动恢复的协议或状态错误会在相关节点的 `details` 中展示，避免主流程图过度复杂。

### 2.6 Luna 执行与结果同步

软件通过 Codex CLI 启动 Luna，并为每个任务提供：

- 任务书内容。
- 当前 Git 基线。
- 治理和架构快照。
- 项目路径。
- 当前模型和推理强度配置。
- 任务范围、保护路径和报告路径。

Luna 必须生成任务报告并返回 `LUNA_RESULT`。对于 `IMPLEMENTATION`：

- 正常完成时同步代码和报告。
- 如果实现证据和报告已经生成，但结果为 `FAILED` 并记录了真实实现或验收阻塞，软件仍会同步代码和报告，让 Sol/CTO 验收。
- 如果是进程失败、结果格式非法、报告缺失、基线变化或保护路径冲突，仍然阻塞。

对于 `TEST`：

- 测试失败属于验收证据，不会阻止报告和测试改动同步。
- 测试任务只能修改 `tests/**` 和任务报告路径。

### 2.7 Git 基线与同步治理

ORCHESTRATOR 拥有 Git 同步权，Luna 不负责提交和推送。

每个任务通常经历以下检查：

1. 捕获任务开始时的本地 HEAD、远端 tip、分支和工作区状态。
2. 启动 Luna 前重新检查基线，防止人工提交或其他进程造成竞态。
3. Luna 修改代码并写入报告。
4. 软件检查报告存在、路径安全、变更范围和保护路径。
5. 软件创建提交并推送远端。
6. 推送成功后更新本轮基线，并通知 Sol。

范围策略如下：

- `IMPLEMENTATION` 允许合理的项目内部范围扩展，但不能触碰保护路径、敏感路径或项目目录之外的文件。
- `TEST` 严格限制在 `tests/**` 和指定报告路径。
- `docs/governance`、架构冻结文件、`.git` 等关键路径受保护。
- Git push 结果必须经过远端状态确认，不能只根据本地命令返回判断成功。

软件还提供人工维护用的“对齐最新 base commit”和“一键 commit/push”能力。这两个操作用于处理阻塞后的工作区对齐，不改变正常自动循环的节点顺序。

### 2.8 治理一致性检查

治理一致性检查是独立入口，不等同于普通 `LUNA_TASK`：

- Sol 根据当前治理模板扫描 `docs/governance` 之外可能产生冲突的文档。
- Sol 输出 `GOVERNANCE_RECONCILIATION` Writing Block。
- 软件读取目标文件的当前内容和规范化 SHA-256，确认覆盖目标没有被意外替换。
- 软件备份旧文件并应用 Sol 返回的新内容。
- 软件提交治理更新并通知 Sol。

如果基线、文件 SHA、远端内容或治理应用器不可验证，软件会阻塞而不是猜测或覆盖文件。

### 2.9 状态持久化、恢复与通知

软件会持久化编排状态，用于处理以下情况：

- 软件重启。
- 用户暂停循环。
- Luna 执行完成但尚未同步代码。
- 同步代码完成但尚未通知 Sol。
- 上下文过长后的会话恢复。
- 可恢复错误和需要用户处理的错误。

前端会显示：

- 当前项目、任务编号和基线。
- 当前连续运行轮次与耗时。
- 项目累计运行轮次与耗时。
- Luna 当前执行时长。
- 当前节点、错误码、恢复节点和下一步动作。

异常状态会通过 Windows 通知提醒用户。涉及外部账号配置、API Key、登录状态、受保护文件或无法安全判断的 Git 状态时，软件会暂停等待人工处理。

## 3. 一次典型使用流程

1. 启动软件并选择或初始化本地项目。
2. 配置远端仓库，确认 Git 授权和工作区干净。
3. 初始化或接管 `docs/governance`。
4. 预览并复制 Sol 系统提示词，放入对应 ChatGPT Project 的背景配置。
5. 打开专用 Edge，登录 ChatGPT，并绑定目标 Project 会话。
6. 使用“启动”开始自动循环。
7. 在 Loop Graph 中观察当前节点和执行计时。
8. 遇到可恢复阻塞时使用“重试”；遇到需要人工确认的状态时先处理外部问题，再选择“继续执行”或“重试”。
9. Sol 收到最新提交和任务报告后进行验收，并生成下一轮任务书。

## 4. 主要目录

```text
src/main/                 Electron 主进程、编排器、Git、Edge、Codex 和治理逻辑
src/renderer/             Dashboard 页面、Loop Graph 和交互样式
src/shared/               Writing Block、Dashboard 和项目配置等共享协议
test/unit/                单元测试和流程回归测试
docs/superpowers/         项目设计文档和实现计划
docs/PROJECT_OVERVIEW.md  本项目说明文档
dist/                     构建输出，不作为源码编辑入口
```

## 5. 开发与验证命令

```powershell
npm install
npm run typecheck
npm test
npm run build
npm start
```

其中 `npm start` 会先构建 TypeScript 和 Renderer 资源，再启动 Electron 应用。

## 6. 项目边界

本项目的目标是自动化“规划—执行—同步—通知”闭环，而不是替代 Sol 的产品判断或 CTO 的最终验收。软件可以校验协议、路径、Git 状态和流程状态，但不能安全地替用户判断：

- 产品方向是否正确。
- 实现是否真正满足业务目标。
- 外部平台账号或 API 配置是否应该授权。
- 报告中的失败是否可以接受。
- 治理冲突是否具备业务上的合理性。

因此，软件在可确定的工程流程上自动执行，在需要产品或安全判断的地方保留明确的阻塞和人工介入边界。
